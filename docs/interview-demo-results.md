# 面试演示实测与失败恢复

2026 年 10 月 18 日完成真实服务联调。最终同一版业务代码的三条正向链路连续两轮通过，另完成越权拒绝和两类建单超时恢复。历史失败记录全部保留；样本很小，不宣称总体准确率或生产性能。

## 实际运行环境

- Python 3.13.16，macOS-26.6.2-arm64-arm-64bit-Mach-O。
- 文本与决策模型：`qwen3.8-max`；视觉模型：`qwen3-vl-plus`；Embedding：`qwen3.7-text-embedding`。
- PostgreSQL 16 + pgvector、MinIO 使用本机既有 ecom-local 容器；临时 API 在 127.0.0.1:8091 启动，运行结束自动退出。没有接入真实商家写接口。
- 每轮新增独立 interview 租户：7 个商品、14 个 SKU、3 条订单明细、1 个政策版本；不覆盖原租户数据。分析库只追加本轮授权投影，不全量重建已有投影。
- 单 Agent 最多 3 次模型决策，共享模型调用上限 8 次；演示任务截止 180 秒。Qwen 思考关闭，答复合成关闭，最终正文由已核验事实生成；决策、政策引句选择、SQL 与视觉识别仍调用真实模型。
- 本轮政策索引显式为 keyword-only，商品走关键词和结构化筛选，向量查询可执行但本轮隔离语料未建向量索引。不将这些记录宣传为向量召回质量评测或完整 GraphRAG 验收。
- 使用用户提供的拖鞋商品图片，人工标签仅用于评测，不写入模型提问。图片 SHA-256：`3f1efa1e01cf61f5472c1bdfa80b7372b56bbade2f1425ff31bbb41555a9077a`。图片价格、品牌或宣传语不作为本店商品事实，卡片价格和库存来自独立沙箱数据库。

### 图片导购

先通过真实上传 API 和 MinIO 保存图片，定向执行本次 OCR/视觉任务，再把 image_id 发给聊天接口。识别结果为“拖鞋”，没有把输入强行归类成跑鞋。

工具轨迹：`shopping.recognize_product → shopping.search_products`。校验真实模型路由、识别品类、授权商品、价格不超过 500 元、库存大于零；不要求与图片同品牌或同款。

### 售后缺货移交

用户选择已签收的本人跑鞋订单，指定 42 码。参考商品 42 码库存为零，其他同品牌候选可售。最终实测工具顺序：

`aftersale.get_owned_order → aftersale.check_inventory → aftersale.retrieve_policy → shopping.search_products`

第一次最终模型调用 7 次。验证政策证据非空、库存核验早于替代检索、结果是同品牌 42 码、不包含原商品，且不突破预算。此聊天不创建换货单。

### 运营 SQL 查询

问题：“按品类统计所有已支付订单明细的支付金额合计，金额单位为分，不限制时间。”

工具轨迹：`analytics.generate_sql → analytics.execute_readonly`。生成 SQL 经过既有 AST/只读与租户店铺范围注入，再与人工基准在同一授权分析数据上执行比较，允许列别名和行顺序不同，但逐单元格数值必须一致。

基准结果：跑鞋支付金额 `95700` 分，即 `957.00` 元。两次模型 SQL 结果均一致；未将 SQL 语法通过当作结果正确。

## 建单超时恢复演示

这里使用真实 API、PostgreSQL 事务和业务处理函数；外部平台响应是明确标注的沙箱故障注入。脚本定向处理本轮 job_id，不启动扫描其他租户任务的常驻 Worker。

### 平台有幂等保障

1. 用户显式提交，使用相同幂等键再提交一次，仍指向同一申请。
2. 自动规则审核通过后首次 create 注入 timeout，状态为 UNKNOWN，任务排队重试。
3. 等待真实退避时间后按相同请求号 probe，返回 missing；回到 APPROVED。
4. 再次等待退避，重新核验政策和订单，再用相同请求号 create；状态 CREATED，Outbox 为 processed。

状态：`UNKNOWN → APPROVED → CREATED`。调用：`create(timeout) → probe(missing) → create(created)`；所有请求号相同。

### 平台无幂等保障

调用仅为 `create(timeout) → probe(missing)`，两次观察均为 UNKNOWN，没有第二次 create。观测点任务/Outbox 仍待处理；这是两轮有限演练，不声称已完成人工核对或最终关单。

原因：超时意味着客户端没有拿到结果，并不能证明远端没有建单。先查询外部状态，只有平台具备幂等保证且确认缺失时才可重发；无幂等保证时保留 UNKNOWN，停止自动创建，等待核对。

最终恢复演练耗时：有幂等 5.241 秒；无幂等 1.972 秒。这是本地故障注入的端到端耗时，不是外部平台恢复 SLA。

## 失败案例与修复过程

| 开发阶段失败 | 实际原因 | 处理 |
| --- | --- | --- |
| 政策检索失败 | asyncpg 无法推断 `:scope IS NULL` 参数类型 | 对可空 scope 显式 CAST 为 text，随后真实 PostgreSQL 检索通过 |
| SQL 结构化输出 400 | Qwen 思考模式不支持强制 tool_choice | 增加显式思考配置，演示关闭思考；不改成伪造 SQL 或固定模板 |
| 售后模型请求超时 | SDK 原连接超时为 5 秒，公网连接偶发超时 | 显式传输超时；只对连接/超时、429 或 5xx 有界重试一次，每次计入共享预算，不重跑业务写工具 |
| 移交后参数校验失败 | 模型额外调用图谱，将 product_ids 生成字符串，产生 list_type 错误 | 移交上下文仅开放 search_products，直接使用已核验事实；普通导购仍保留其他工具 |
| 潜在错误费用展示 | 未配置模型价格时显示近似 0 元 | 改为 unknown，不把未知费用写成免费；费用以供应商账单为准 |

最初失败记录与中间复测均见 [证据索引](interview-evidence/index.json)，没有删除失败来计算通过率。不同修订的数据不能合并为同一个模型准确率。

## 保存的证据与验证范围

- 每个场景 JSON 保存实际请求、SSE 事件及时间、工具轨迹、结构化结果、是否通过；SQL 额外保存人工基准和执行结果。
- 恢复 JSON 保存每轮工单与任务状态、退避时间、适配器操作和稳定请求号。
- 最终两轮报告记录实际成功模型调用的 token 和耗时。Embedding token 不计入该精确合计；失败尝试可能没有供应商 usage。未配置可靠价格，不估算总费用。
- 归档只包含允许导出的 JSON/摘要，不包含 API 日志、访问令牌、签名上传链接、模型密钥或完整用户原图。原始运行目录在 `evals/reports/`，被 .gitignore 排除；脱敏证据在 `docs/interview-evidence/` 可随项目交付。
- 自动化回归：341 项通过；固定离线评测：62/62。因增加拖鞋词表，原未知词用例换为仍不支持的登山杖，另增拖鞋映射用例，并显式重新锁定摘要；没有用修改预期掩盖上述线上失败。
- 这份材料证明小规模沙箱场景的真实模型执行、约束和恢复路径，不证明真实平台接入、总体准确率、生产 P95、全部十指标在线正确率或大规模向量检索质量。

## 一键复现

先启动已有本地基础设施并确认业务迁移到 0003、分析表已初始化、MinIO 桶可用，配置有效的文本和视觉密钥。对新环境先按 README 初始化；脚本不会为了演示清空已有分析库。

```sh
.venv-ecom/bin/python -m scripts.interview_demo \
  --image "/Users/jingjing/Desktop/995e48d916ca0174ce4d3c9fa18c38c7_副本3.png" \
  --expected-category 拖鞋 \
  --vision-model qwen3-vl-plus \
  --start-api
```

更换图片时同时修改人工标签；标签只参与评测。API 默认临时使用 8091 端口，若占用则用 `--port` 更换。`--only image_shopping aftersale_handoff analytics_sql` 可仅复测三条正向链路。每次生成独立租户和新报告目录，失败退出码为 1，原报告不会覆盖。

演示语音讲解建议：先展示图片识别及两条商品卡，再展示售后/导购工具移交，接着打开 SQL 与基准结果，最后展示 UNKNOWN 状态时间线并解释为什么不能立即重发。
