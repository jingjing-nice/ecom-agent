## 在线验收依赖

容器联调已实际尝试：Docker Desktop 可连接，但原 MinIO 镜像不可拉取，同版本 Quay 返回 401；已新增固定上游版本源码构建路径。随后构建基础 Go 镜像时 Docker Hub 认证端点网络超时，初始化在迁移前停止。源码构建路径仍待网络恢复后验证，不能报告容器已经启动成功。

需继续执行：

- `sh scripts/bootstrap.sh`：真实迁移、种子、图谱、分析同步、MinIO 和应用启动。
- `python -m scripts.demo_smoke`：真实 API 冒烟。
- `python -m scripts.eval_run --live`：路由、政策拒答、生成 SQL 与人工基准执行结果对照。
- `python -m scripts.checkpoint_drill --run`：Redis Stack 跨进程恢复。
- `python -m scripts.loadtest --help` 后按实际机器设置参数并记录数据规模与 P95。
- PostgreSQL 真实并发提交、重复审核、RLS 反例、Worker 重启、对象上传签名及模型 OCR。

## 数据与恢复

初始迁移是固定 SQL 快照。新增商品索引由 `0002_product_search` 创建，禁止用修改初始迁移代替升级。当前迁移固定向量维度为 1024，更换维度需要新增迁移。

分析投影与同步水位在一个事务内替换；源事实使用只读可重复读快照。查询端也用只读可重复读事务，展示授权店铺最早同步水位；任一授权店铺缺水位时不展示完整性时间。

备份命令（数据库启动后）：

```sh
docker compose exec -T postgres pg_dump -U ecom -d ecom_db -Fc > ecom-demo.dump
```

恢复先建独立数据库，在其中恢复并检查迁移版本、租户权限、订单和售后状态，再切换配置。分析投影、商品索引与图谱可分别通过 analytics_sync、catalog_index、graph_seed 重建。备份恢复演练尚未执行，不承诺生产 RPO/RTO。


## 模型 RAG 替换更新

知识切片现使用 LangChain 官方分窗组件与 LangGraph 模型语义分组，检索改用 LangChain Retriever / Embeddings 接口和串行 RAG Runnable。原手写段落/句子切片实现已移除；离线 split_text 兼容接口只委托官方组件，不参与在线入库。异步任务保存原文和哈希，切片落库后复用，发布仍需审核和索引校验。

当前无 Embedding 密钥时保留显式 keyword-only 索引，不能称为完整向量 RAG 验收。旧版本需重新导入新版本才能使用模型切片。新流程没有新增数据库结构，需安装更新后的锁文件并重建应用镜像。

## 全自动客服方向更新

按用户确认的目标，售后不再以客服审批为正常链路。新增迁移 `0003_automatic_aftersale` 为政策版本保存可校验的自动规则；默认开启 `AFTERSALE_AUTO_REVIEW`，提交与补料在同一事务投递自动审核任务。Worker 核验政策、订单归属、状态、人民币明细金额、期限及原始 OCR 凭证，通过后写审计、outbox 与建单任务。外发前重查规则，重复投递和已取消任务跳过。前端移除转人工、人工回复和客服审批操作。

当前自动处理仅覆盖退款及退货退款的沙箱申请建单。换货的目标 SKU 选择、库存预留、部分退款、退货验收和真实资金操作没有交付。规则缺失或有歧义时暂停执行，NEED_MORE_INFO 返回受控原因；政策配置属于事前经营设置，不是每单人工审批。历史人工接口保留兼容，旧人工工单不自动迁移。新环境种子包含明确的演示自动规则，已有租户须通过新版本导入发布，不覆盖原政策。

故障处理：自动工单 UNKNOWN 后先核对；有幂等保证且 missing 时回到 APPROVED，复核后使用同一请求号重试，无幂等保障时保留 UNKNOWN，仅重试核对至任务重试上限。

测试中另发现初始快照对政策 status 单列索引与复合索引使用同名，导致新库初始化失败；仅修正复合索引名称并同步 ORM，没有改写已存在表或数据。真实 PostgreSQL 迁移、锁竞争与容器运行仍需集成验收。

## 企业统一聊天入口

运营演示账号现在在同一个聊天页面与同一 conversation_id 中使用三类 Agent：商品咨询委派 shopping，订单状态委派 aftersale，指标统计委派 analytics。新增 list_orders 只读工具，按完整订单号精确过滤或列出最近 20 笔授权订单；无需先在侧栏手工选单。返回结构化订单卡片，分析结果在消息内显示表格和图表。

权限同步调整：ops 可以读取授权店铺的商品及订单，不再仅能查询聚合数据；没有获得买家售后写权限。buyer 仍只读本人订单，不能调用 analytics。租户与店铺过滤在订单服务和工具内执行，不接受模型提供授权范围。默认登录演示角色调整为 ops，买家和知识管理入口保留。

图谱服务缺失时禁止驱动长时间自动重试，连接与连接池等待各限制为 3 秒，避免图谱候选的附加查询拖垮普通导购。

统一入口回归：313 项测试通过，前端 TypeScript/Vite 构建通过。新增测试验证订单工具在运营授权店铺内读取、跨租户及跨店铺隔离、不授予售后写权限，以及无需选单的订单路由。在线测试的商品和订单两步已通过；SQL 模型生成遇到 30 秒超时，新增 `SQL_MODEL_TIMEOUT_SECONDS`，本地设为 60 秒，任务总时限设为 120 秒；数据库 SQL 执行仍为 5 秒，模型超时和数据库超时分别控制。

## Agent 简化与恢复修正

子 Agent 运行次数由 LangChain `ModelCallLimitMiddleware` 控制；跨 Supervisor、RAG 和摘要的总模型预算继续由请求运行时管理。整批工具预校验、授权与同一 AsyncSession 串行执行仍保留。工具转发保留完整 `tool_call` 类型，避免把调用信封误当作业务参数。模型工具绑定返回副本，避免修改共享适配器。

Supervisor 的已访问 Agent、结果、工具输出、模型/工具计数、移交信息和轨迹在节点边界写入检查点。重建图后从已完成的委派边界恢复这些事实，数据库连接与当前授权对象每次重新创建。子 Agent 内部尚未独立持久化：委派节点执行中崩溃时，该节点的只读查询可能重跑；这不构成任意工具边界的恰好一次执行保证。

`CHECKPOINT_BACKEND=postgres` 使用官方 `AsyncPostgresSaver.from_conn_string()` 和 `setup()`，不传 Redis 专属 TTL。`CHECKPOINT_TTL_MINUTES` 仅作用于 Redis，PostgreSQL 需要另行安排数据清理。切换后端先释放旧连接。普通 Redis 7 无法承载 Redis Stack 检查点，本地可选 PostgreSQL。

`AGENT_HUMAN_APPROVAL=true` 时，聊天中的待确认建议暂停，并展示“确认建议/取消”。`POST /v1/chat/approve` 接收 `conversation_id`、`client_message_id` 与 `decision`（`APPROVED` / `REJECTED`）；线程和原始有效请求从服务端消息记录读取。恢复时核验线程所属用户、租户、角色、店铺授权和原始请求，按会话行锁串行处理；同一决策可重放，相反决策拒绝。检查点恢复成功但消息事务未提交时，可重试同一决策补写消息。此入口只确认咨询建议，不创建工单或执行退款；生产多进程部署须使用持久化检查点。

模型熔断按模型分别计数，视觉成功不会清除文本模型故障，文本故障也不会阻断视觉调用。流式和非流式计量复用同一实现。未新增 LiteLLM、Langfuse 或 Celery 服务；任务调度与长事务拆分涉及 Outbox 及外部状态核对，需要单独迁移验证。

## 业务层与任务生命周期收敛

聊天的会话归属、幂等消息重放、槽位继承、Agent 执行及建议确认统一放到 `src/services/chat.py`；路由只处理认证依赖、提交边界和 SSE 编码。响应封装移到 `src/api/responses.py`，上传与知识路由不再依赖主路由模块。原有 URL 和事件名称保持兼容，流正常结束前完成消息提交；中途失败回滚，流关闭时显式关闭下层生成器和数据库会话。

任务入队、成功、最终失败与 Outbox 终态同步集中到 `src/services/jobs.py`。成功重试会清除上一次的错误和退避时间；重试等待期间不把 Outbox 标为失败。Worker 在一次任务处理结束后统一同步 Outbox，覆盖处理函数提前返回的分支。入队不隐式提交，售后审核、业务状态和外发事件继续保持同事务。

售后状态迁移统一通过 `transition_case` 校验并递增版本；需要并发版本核对的服务共用 `get_case_for_update`。凭证读取统一由 `load_refund_evidence` 按租户、本人、凭证用途及识别状态过滤，一次批量读取，避免逐张查询；锁定时按 ID 排序。草稿校验要求全部凭证有效，自动审核只使用授权且已提取的原始 OCR 数据。

本轮不增加依赖或数据库迁移。Worker 仍使用原有事务内行锁，不改为租约领取；长事务及外部写入核对的迁移仍需真实 PostgreSQL 并发和故障演练后单独实施。
